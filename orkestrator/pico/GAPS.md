# Pico — Gap Analysis vs Foundry

Scope: feature/behavior gaps only, not language/framework structural differences.
Foundry = `orkestrator/foundry/` (Python/FastAPI + React/Vite, mature reference).
Pico = `orkestrator/pico/` (TypeScript/Node/Express + React/Vite, lighter reimplementation).
Also reviewed: `orkestrator/.pico-foundry-src.html`, an 18-module tutorial that documents the
intended design of Pico Foundry (a teaching project distinct from, but architecturally
identical to, the `pico/` code in this repo).

## Backend gaps

- [ ] **Context stage silently dropped from the UI pipeline view.** `pico/src/types.ts:46-52` — the exported `PIPELINE` array has `"context"` commented out (`// "context",`), so `PIPELINE = ["fetch","plan","implement","verify","pr"]`. But `pico/src/pipeline.ts:14-21` defines its own local `STAGES` const that *does* include `"context"`, and `runTask()` genuinely executes and records a `context` stage (`pico/src/pipeline.ts:38-40`). Since `projectStages()` (`pico/src/projection.ts:14-36`) iterates `PIPELINE` (not `STAGES`) to build the `StageView[]` sent to the frontend, the context stage's events exist in the log but never appear as a step in the UI stepper. The frontend's own `PIPELINE` constant (`pico/web/src/types.ts:63`) includes `'context'`, diverging from the backend's actual runtime list — the two "mirrors" have drifted.
- [ ] **Session resumption for CLI retries is dead.** `pico/src/agents/cli.ts:53-54` hardcodes `const resumeId = ""` with the real lookup commented out (`// getSession(task.id, stage);`). `saveSession()` is still called on success (line 165), so sessions are persisted but never read back — every retry attempt starts a brand-new Claude CLI session instead of resuming, contradicting the interface's stated purpose (`sessionId` exists specifically so retries can continue a conversation, per the tutorial's module 10 note).
- [ ] **No security/sandboxing layer at all.** `pico/src/shell.ts` (`run()`, lines 9-29) has no command allowlist/denylist, no cwd-based dangerous-command check, and no path confinement — none of `assertCommandAllowed`, `safeJoin`, or `scrubbedEnv` exist anywhere in `pico/src/` (confirmed via full-tree grep; there is no `security.ts`). Foundry has all three in `security.py`.
- [ ] **Full, unscrubbed environment leaked into every agent subprocess.** `pico/src/agents/cli.ts:69` spawns the `claude` CLI with `env: process.env` — the complete parent environment, including `GITHUB_TOKEN` and any API keys. A `agentEnv()` allowlist helper is defined right above it (lines 18-34) but is never called anywhere in the file — dead code that would have fixed exactly this.
- [ ] **Config bootstrap uses an undefined identifier.** `pico/src/config.ts:12` — `githubToken: required("GITHUB_TOKEN")` calls a name that does not resolve to the `required()` helper defined two lines above (which every other config field uses, e.g. line 13 `repo: required("GITHUB_REPO")`); as written this throws a ReferenceError at startup.
- [ ] **`resume` route doesn't clear cached stage results — blocked tasks can't actually be unblocked.** `pico/src/api/tasks.ts:57-71` sets the task back to `{status:"pending", stage:"fetch"}` but never deletes rows from `stage_results`. `pico/src/state.ts` has no `clearStageResults()` function at all. Because `pipeline.ts`'s `once()` helper (lines 102-121) checks `getStageResult()` before rerunning any stage, resuming a blocked task will hit the cached `plan` result, return the same `needsHuman: true` verdict, and immediately re-block — even after the human answered the questions on the issue. This is precisely the pitfall the tutorial calls out by name in module 11 ("Тонкость, о которой легко забыть") and gives as a required task item with a reference `clearStageResults` implementation.
- [ ] **Blocked tasks never notify the human via the GitHub issue.** `pico/src/pipeline.ts:45-50` — on `needsHuman`, pico only records a `blocked` event and updates task status; it never calls `commentOnIssue()`. The tutorial's reference solution for the same branch explicitly posts the agent's questions as an issue comment so a human actually sees them without opening the UI.
- [ ] **No repo memory / cross-task learning at all**, despite the tutorial's own "what we simplify" table (§a5) stating Pico Foundry should have a *simplified* version ("файлы удачных задач и последние провалы"). Grep across `pico/src/` for `repo_memory`/`touched_files`/`verify_command`/`common_failures` returns zero hits — no table, no read/write logic, nothing threaded into `context.run()` or prompts. Foundry has the full `repo_memory` table + `_save_successful_pr_memory` plus a UI card.
- [ ] **Only one real agent backend** (`claude_cli`, `pico/src/agents/cli.ts`) plus a stub (`pico/src/agents/stub.ts`); no `codex_cli` / `opencode_cli` equivalents. Foundry supports four backends behind `CodingAgent`/`make_agent(settings)`. (Tutorial module 10 explicitly frames this as an intentional, acceptable simplification — not a bug — but it is still a capability gap relative to foundry.)
- [ ] **Two-tier verification with structured failure classification is absent.** Pico's `verify.ts` runs a single shell command with a pass/fail result and a flat `maxAttempts` retry (`config.maxAttempts`, default 2) with no failure-type distinction; foundry classifies failures into 5 categories (deterministic/acceptance/infra/unclear/dangerous) driving different retry/block/fail decisions.
- [ ] **No PR-feedback workflow.** Once `pr.run()` succeeds, the task is `done` and its worktree is removed (`pico/src/pipeline.ts:86-87`) — there is no loop that re-reads CI/review status on the opened PR and pushes follow-up commits. Foundry has a dedicated `pr_feedback` workflow. (Tutorial module 17 lists this as a stretch goal even for the reference project, so it's a "both are missing this by design" item, included here for completeness since foundry does have it.)
- [ ] **`worktreeTest()` is broken debug scaffolding left wired into the API.** `pico/src/worktree.ts:8-12` calls `agent.apply(getTask(1), "orkestrator/pico/worktrees/_base")` — 2 args where `CodingAgent.apply` requires 4 (`task, worktree, input, stage`), and hardcodes task id `1` and a relative path. It's exposed via a "Worktree Test" button in `pico/web/src/components/Layout/Header.tsx`, so clicking it in the running UI throws.
- [ ] **Duplicate/dead imports left in `agents/cli.ts`**: `saveSession` is imported four times (`pico/src/agents/cli.ts:5-9`), `getSession` is imported but never called (only appears commented out at line 54), `import { response } from "express"` (line 16) is unused/shadowed by the local `let response = ""` (line 91).
- [ ] **`pico/src/stages/context.ts` context-building has no ranking**, unlike foundry's TF-IDF file ranking + language/manifest detection (`context.py`). Pico's `buildContext()` (`pico/src/agent.ts`) does a naive filename-keyword match against the issue title, capped at 5 files. (Tutorial §a5 actually specifies Pico Foundry should do *no* context collection at all and let the agent read files itself — pico's naive keyword filter is a third, undocumented middle ground, neither foundry's nor the tutorial's baseline.)

## Frontend gaps

- [ ] **Cost/token/agent-name data is entirely client-side fabricated.** `pico/web/src/lib/mock.ts` — explicit top-of-file comment states this is data "the backend doesn't provide yet." Contains `MOCK_REPO`, a seeded `hashUnit()` pseudo-random function, a hardcoded `AGENT_BY_STAGE` map, and `stageTokens()`/`taskTokens()`/`tokensToUsd()` that derive fake tokens from `stage.durationMs` with per-task jitter. This underlies nearly all cost/token/agent UI in pico. Foundry computes and transmits these fields for real (`tokens_in`/`tokens_out`/`cost_usd`/`agent` on stage/event payloads), and its `liveTaskProjection.ts` threads them live; pico's `lib/liveTask.ts` `projectLiveTask()` can only thread `status`/`durationMs` because the backend payloads lack the rest.
- [ ] **Sidebar is 100% static/hardcoded.** `pico/web/src/components/Layout/Sidebar.tsx` — no props, no data fetching: hardcoded "Задачи" badge `2`, hardcoded "the-foundry" repo nav item with hardcoded badge `2`, hardcoded "Сегодня" token-spend text `"1491.3k ток."` as a literal string. Foundry's `Sidebar.tsx` takes real `{repos, tasks}` props and computes `todayTokens` from actual DONE-task data.
- [ ] **Header "Run" button is completely non-functional and looks enabled.** `pico/web/src/components/Layout/Header.tsx` — `<Button color="violet" leftSection={<IconPlayerPlay/>}>Run</Button>` has no `onClick` at all. Foundry's equivalent (`Topbar.tsx`) is deliberately `disabled` with an explanatory tooltip ("Запуск из UI появится позже...") — same missing feature, but foundry visually communicates it while pico's silently does nothing when clicked.
- [ ] **Header search input is cosmetic only.** `pico/web/src/components/Layout/Header.tsx` renders a `TextInput` with no `value`/`onChange` wiring. Foundry's `Topbar.tsx` wires search to `searchQuery`/`onSearchQueryChange`, which actually filters the task list (`matchesSearch` in both codebases' filter libs — pico's `lib/filters.ts` supports the same search fields, it's just never fed by the UI).
- [ ] **Dead/orphaned component subtree: `TaskExpandedContent.tsx` and everything under it.** `pico/web/src/components/Tasks/TaskExpandedContent.tsx`, `StageDetail.tsx`, standalone `StageIO.tsx`, standalone `AgentBadge.tsx`, standalone `AskAgentComposer.tsx` are fully built but never imported from `App.tsx` or `TaskRow.tsx` (confirmed via reverse-import grep). The actually-live expanded-row panel is `TaskView.tsx` (990 lines), which duplicates all of this logic locally with slightly different prop shapes (e.g. its inline `AgentBadge({name, model})` vs. the dead standalone's `AgentBadge({agent: AgentInfo})`) — meaning two parallel, diverging implementations of the same feature exist, and only one is reachable.
- [ ] **User-visible corrupted column headers.** `pico/web/src/components/Tasks/TasksTable.tsx` — the `COLUMNS` array renders raw placeholder strings as literal table headers: `title: 'Статус'` (status column), `'Задача'` (task column), `'Стадии'` (stages column), `'Длит.'` (duration column). This is the most user-facing occurrence of a corrupted-identifier artifact found in either codebase (other occurrences are in comments/dead code, e.g. `TaskView.tsx:964` `Таймлайн стадий`, which also appears verbatim in foundry's `TaskDetails.tsx`, confirming shared source lineage).
- [ ] **No Reset feature.** Foundry's `TaskDetails.tsx` has a full reset flow (`resetMutation` → `resetTask(task.id)`, `window.confirm()` guard, `canReset = status !== "RUNNING"`, invalidates `['tasks']`/`['repos']`). Pico has no equivalent action or endpoint.
- [ ] **No "Repo memory" UI card** — direct consequence of the backend having no repo-memory feature at all (see Backend gaps). Foundry's `TaskDetails.tsx` renders one, iterating `task.memory`.
- [ ] **`agent_thinking` and `agent_result` event kinds are entirely unsupported.** Pico's `EventKind` type (`pico/web/src/types.ts:14-20`) only has 6 values (`stage_started/finished/failed`, `agent_text`, `agent_tool`, `blocked`) and `useTaskStream.ts`'s `KINDS` array matches exactly — there is no way for pico's backend or frontend to ever produce or render a "thinking" (🧠) or "final result" (📝) event, both of which foundry's `EventStream.tsx` explicitly renders.
- [ ] **No streaming-error surface.** `pico/web/src/hooks/useTaskStream.ts`'s `Stream` interface is `{task, events, connected}` — no `error` field. Foundry's `useTaskStream.ts` exposes `.error`, surfaced in `TaskDetails.tsx` as "Поток событий: {streamError}"; pico gives no UI feedback if the SSE connection fails.
- [ ] **No stage-alias / canonical-stage-metadata layer.** Foundry has `stages.ts` (`STAGES: StageMeta[]`) mirroring backend `STAGE_ALIAS`, mapping internal FSM stage names to UI-facing ones. Pico has no equivalent single source of truth — stage labels are inlined ad hoc (`STAGE_TITLE` in `pico/web/src/types.ts:62-69`) with no alias concept, consistent with pico's FSM having no aliased/renamed stages to begin with.
- [ ] **`StageIO` renderer has no "pending" state.** Foundry's `StageIO.tsx` renders a `{kind:"pending"}` shape as a spinner + "в процессе…". Pico's `StageIORenderer` (inline in `TaskView.tsx`) only branches on null/string/string[]/plain-object, with no in-progress placeholder.
- [ ] **`FilterBar` has no dedicated "blocked" tab in foundry** — this is actually a place pico is *ahead*: pico's `TaskFilter` (`pico/web/src/lib/filters.ts`) has 5 states including a dedicated `'blocked'` tab with orange badge coloring (`TaskFilters.tsx`); foundry's `FilterBar.tsx` only has 4 (`all/active/done/failed`), with blocked tasks presumably folded into "active." Noted as a gap in the other direction / worth carrying back if foundry is ever revisited.

## Notes from .pico-foundry-src.html

This file is an 18-module tutorial ("Pico Foundry — Учебник") that documents the *intended*
design for a project structurally identical to `pico/`. Its nav marks modules 0-9 (stack/FSM/
storage/event log/orchestrator/HTTP API/SSE/React UI/GitHub Issues/git worktree) as `class="done"`
and modules 10, 11, 12, 13, 14, 16, 17 as not-done — closely matching where the real gaps above
cluster (agent interface & security in particular).

- **§a5 "Что мы упрощаем" (what we simplify)** is an explicit table of intended simplifications vs. foundry, useful as a baseline for what should and shouldn't count as a gap:
  - Agent: one `CodingAgent` interface, two impls (stub + CLI) — codex/opencode intentionally unsupported.
  - Context collection: intentionally none (agent reads files itself) — pico's actual naive keyword-filter `buildContext()` is a third, undocumented middle ground.
  - Verification: one command from `.env`, no auto-detection by language — matches pico.
  - Retry: two attempts + `git reset --hard`, no failure classification — matches pico.
  - Repo memory: tutorial says pico *should* have a simplified version (files of successful tasks + recent failures) — **pico's actual source has none at all**, a real gap even against the tutorial's own reduced baseline.
  - PR-feedback: intentionally absent in both tutorial-pico and real pico.
  - Tests/Docker: intentionally absent.
  - Explicitly NOT simplified (should be full-strength): FSM/transitions, stage idempotency, append-only event log, SSE stream, worktree isolation, two-tier verification, retry loop, the BLOCKED branch, and the security layer — pico's actual security layer being completely absent (no `security.ts` at all) is therefore a deviation from the tutorial's own stated non-negotiables, not just an accepted simplification.
- **Module 11 ("PLAN и остановка ради человека")** gives the exact reference implementation for the human-in-the-loop block/resume flow, including the `clearStageResults()` requirement on resume and the `commentOnIssue` call on block — both of which pico's actual code omits (see Backend gaps above). It also stresses checking only the *last non-empty line* for the `NEED_HUMAN` marker (to avoid false positives when the model discusses the marker in prose) — pico's `needsHuman()`/`stripMarker()` (`pico/src/stages/plan.ts`) do get this part right, using `.at(-1)` and a regex on the last line only.
- **Module 14 ("Слой безопасности")** frames the threat model explicitly: issue bodies are untrusted input that flows into prompts, and model output becomes files/commands, so a filter must sit between "model said" and "system did" without asking the model's permission. It specifies exactly three required functions — `assertCommandAllowed` (denylist: `rm -rf`, `git push --force`, `git reset --hard` outside the task's worktree, `sudo`, `curl|sh`), `safeJoin` (path confinement), `scrubbedEnv` (allowlist-based env for subprocesses) — and insists the check must live inside `shell.run` itself (the single choke point), not at call sites, "because a check you have to remember to call will eventually not be called." Pico has none of the three, and its one choke point (`shell.ts`'s `run()`) does no validation at all.
- **Module 16 ("Долгая память")** specifies three memory keys the reference should persist per repo after every successful PR: `touched_files`, `verify_command`, and — called out as the most valuable — `common_failures` (failed verification reports), explicitly noting this information exists *only* in the event log/stage-results tables and is unrecoverable from git history alone (failed attempts get `git reset --hard` away). This underscores that pico's total absence of repo memory is a loss of genuinely irrecoverable information, not just a nice-to-have.
- **Module 17 ("Куда расти дальше")** is an explicit stretch-goals list, not a "should already have" list — it names PR-feedback loops, a stub agent for offline runs, patch-based (vs. full-file) edits, parallel task execution with rate-limit handling, and a test/Docker suite, all as *future* work even for the tutorial's own reference implementation. These are noted here for completeness but should not be weighted as heavily as the modules 10-14/16 gaps, which the tutorial treats as core, unfinished material.
