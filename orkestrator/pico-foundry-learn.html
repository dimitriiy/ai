Pico Foundry

Сначала разбираем как устроен The Foundry — оркестратор который превращает GitHub issue в готовый pull request. Потом собираем его уменьшенную копию на TypeScript и React, своими руками, шаг за шагом.

Документ состоит из двух частей. Часть A — разбор боевого проекта: какую задачу он решает, из чего собран и почему собран именно так. Часть B — курс: восемнадцать модулей, каждый со своей теорией, заданием, способом самопроверки и эталонным решением.

Курс написан с расчётом на фронтендера: всё что относится к бэкенду — процессы, базы, git, запуск внешних программ — объясняется с нуля. Термины разбираются во врезках «определение» там где встречаются впервые. React, Vite, TypeScript и SSE со стороны браузера наоборот не разжёвываются.

Особенность курса: модули идут в формате v0→проблема→v1. Сначала делаешь наивно, сталкиваешься с конкретной проблемой, потом чинишь. Так каждое решение получает оправдание.

Часть A

Что делает The Foundry

Представь очередь мелких задач по репозиторию: поправить валидацию, добавить поле в ответ API, обновить текст ошибки. Каждая занимает у человека двадцать минут из которых пятнадцать — переключение контекста. The Foundry берёт такие задачи на себя целиком: читает issue с определённым лейблом, разбирается в репозитории, пишет план, пишет код, проверяет его тестами и вторым LLM-ревьюером, открывает pull request и закрывает issue.

Ключевое слово здесь — оркестратор а не «обёртка над LLM». Разница принципиальная и именно она и есть предмет изучения.

Оркестратор — программа которая не делает работу сама а управляет порядком её выполнения: что запустить в каком порядке что делать при сбое когда остановиться. Здесь работу делает языковая модель а оркестратор решает когда её позвать с каким запросом и что считать приемлемым результатом. Ближайшая аналогия из фронтенда — роутер: страницы рисуют компоненты но какая страница сейчас открыта и что будет при переходе решает не компонент.
Конечный автомат (finite state machine, FSM) — способ описать поведение через конечный список состояний и разрешённых переходов между ними. Задача всегда находится ровно в одном состоянии («сейчас идёт планирование») и перейти может не куда угодно а только туда куда разрешает схема. Ты сталкивался с этим в UI-стейт-машинах: idle → loading → success | error и из idle нельзя попасть сразу в success. Здесь ровно то же только состояния — это стадии обработки задачи.

Агент никогда не решает какая стадия следующая — даже если очень попросит.

Схема архитектуры

Физически это три независимых процесса которые не знают друг о друге ничего кроме пути к общему файлу SQLite.

Процесс — запущенная программа со своей памятью. Два процесса не видят переменные друг друга: массив положенный в память одного для второго не существует. Поэтому всё чем они обмениваются должно лежать снаружи — в файле базе или по сети. Это главное отличие от фронтенда где весь код живёт в одной вкладке и общая переменная работает. Здесь worker и API — разные программы запущенные разными командами возможно в разное время.

Обрати внимание: между процессами нет ни очереди ни брокера ни сокетов. Worker пишет строки в SQLite API их читает — раз в полсекунды опрашивая таблицу событий. Это выглядит примитивно и это осознанный выбор: одна точка правды ноль инфраструктуры полная переживаемость рестарта. Пока задач десятки а не десятки тысяч такой «брокер» честнее любого Redis.

Брокер сообщений — отдельная служба (RabbitMQ Kafka Redis и подобные) через которую процессы передают друг другу сообщения: один кладёт другой забирает. Стандартное решение для связи между процессами — и ещё одна программа которую надо поставить настроить мониторить и чинить. Здесь его роль исполняет обычная таблица в SQLite а «доставка» — это то что читатель периодически перечитывает таблицу.

Стадии пайплайна

Стадии линейны и однонаправленны — единственная петля — это implement → verify → implement.

Детерминированный — дающий один и тот же результат на одних и тех же входных данных. Запуск тестов детерминирован: прогнал дважды — получил то же самое. Запрос к языковой модели — нет: тот же промпт может дать разный ответ. Отсюда практическое следствие на котором держится вся верификация: детерминированной проверке можно верить как факту недетерминированной — только как мнению.
СтадияДетерм.Что делает
FETCHдаgh issue list по лейблу сортировка по priority upsert в SQLite
CONTEXTдасканирует worktree: языки манифесты релевантные файлы тестовые команды
PLANнетагент пишет план; если задача неясна — терминальный маркер NEED_VERIFICATION
IMPLEMENTнетагент правит файлы в worktree
VERIFYсмешанная① тесты и линтер (короткое замыкание) ② LLM-ревьюер по diff

Порядок внутри VERIFY выбран не случайно. Сначала гоняются дешёвые детерминированные команды и если код не компилируется — LLM-ревьюер не вызывается вообще. Это экономит деньги и что важнее не даёт модели «отревьюить» заведомо сломанный код и сказать что всё хорошо.

Ключевые решения ради которых всё это стоит изучать

  1. SQLite как единственная точка правды. Четыре таблицы: tasks (состояние) task_events (лог) stage_results (результаты стадий) repo_memory (долгая память). Убивает необходимость в брокере кэше и session storage разом.
  2. Журнал событий в который только дописывают. Отдельная таблица куда каждый шаг добавляет строку «что произошло» — и где ничего никогда не меняют и не удаляют. У каждой записи есть seq: порядковый номер внутри своей задачи (1 2 3…) который только растёт.
  3. Стадию можно безопасно запустить повторно. Прежде чем работать стадия проверяет не сохранён ли уже её результат; если сохранён — ничего не делает и возвращает готовое. Свойство называется идемпотентностью.
  4. Каждая задача работает в своей копии репозитория. Механизм git worktree позволяет иметь несколько рабочих папок поверх одной скачанной истории.
  5. Двухуровневая верификация. Машина проверяет то что умеет проверять машина; модель проверяет то что тесты поймать не могут — соответствие изменений замыслу issue.
  6. Повтор попытки с откатом и памятью о провале. Перед новой попыткой изменения предыдущей сохраняются в отдельный файл-снимок а рабочая копия возвращается в исходное состояние командой git reset --hard.
  7. Человек как явная ветка автомата. Не «упало и висит» а статус BLOCKED вопрос комментарием в issue и эндпоинт /resume. Непонимание задачи — это штатный исход а не ошибка.
  8. Агенту не доверяют. Перед запуском любой команды проверяется чёрный список запрещённых. Запускаемым программам передаётся урезанный набор переменных окружения — без токенов и ключей.
Часть B · Курс

Как проходить

Модули идут в единственно правильном порядке. Первые восемь строят ходячий скелет: пайплайн с фальшивыми стадиями но с настоящим логом событий настоящим API настоящим SSE и настоящим UI. Уже на седьмом модуле ты видишь в браузере как задача едет по стадиям. Дальше фальшивые стадии по одной заменяются на настоящие — GitHub git LLM — и каждая замена сразу проверяется в том UI который уже работает.

Это противоположно порядку «сначала логика потом интерфейс» и это сознательно: наблюдаемость в такой системе не украшение а инструмент отладки. Без неё модули 10–13 отлаживаются вслепую.

Про эталонные решения. Они полные и рабочие но нарочно без обработки ошибок ретраев и валидации входа — ровно как договаривались. Если твой код отличается от эталона это не значит что он хуже: сравнивай не буквы а решения. Расхождение в решении — повод разобраться.

МОДУЛЬ 00

Постановка и стек

Договариваемся, что именно строим, и заводим пустой каркас, который запускается.

Теория

Pico Foundry — это два процесса и одна база:

  • worker — берёт задачи из GitHub, гоняет по стадиям, открывает PR;
  • api — отдаёт состояние задач в UI и стримит события;
  • web — React-приложение (формально третий процесс, но только в разработке — это Vite dev server).

Почему такой стек:

ВыборПочему
better-sqlite3Синхронный API. В пайплайне вся работа последовательная, и синхронные вызовы убирают целый класс ошибок с гонками. Асинхронный драйвер здесь ничего не даёт.
tsxЗапуск TypeScript без шага сборки. Для учебного проекта шаг сборки — чистые накладные расходы.
expressНужны четыре роута и один стрим. Fastify/Nest здесь — оверинжиниринг.
@octokit/restТипизированный клиент GitHub API. Альтернатива — дёргать gh CLI как подпроцесс, как в оригинале; SDK честнее для TS-проекта.
@anthropic-ai/sdkПрямой вызов Claude. Никакого CLI-агента, никакого tool-use цикла.
React без state-библиотекВсё состояние — это список задач и поток событий. useState + useEffect хватает, а React Query спрятал бы ровно ту механику, которую мы изучаем.

МОДУЛЬ 01

Доменная модель и конечный автомат

Самый важный модуль курса: здесь решается, кто в системе главный.

Теория

Соблазн при постройке агентной системы — дать модели решать, что делать дальше: «вот тебе инструменты, вот задача, действуй». Это работает в демо и разваливается в проде, потому что у такой системы нет наблюдаемого состояния. Нельзя ответить на вопрос «где сейчас задача №7 и почему она там застряла».

Поэтому первое, что мы фиксируем в коде, — конечный автомат. Множество стадий конечно, переходы описаны таблицей, и переход выбирает оркестратор на основании типизированного результата стадии. Модель влияет на выбор только через данные (прошла верификация или нет), но не через управление.

У нас две ортогональные оси, и их важно не путать:

  • Stage — где задача находится: fetch → plan → implement → verify → pr → done. Плюс терминальная failed.
  • TaskStatus — что с ней происходит: pending (ждёт), running (в работе), blocked (ждёт человека), done, failed.

Задача может быть blocked на стадии plan — это две разные вещи, и хранить их надо раздельно. В оригинале ровно так: tasks.current_stage и tasks.status — две колонки.

Терминальное состояние — состояние, из которого нет выхода: попав в него, задача больше никуда не перейдёт. У нас терминальны done и failed. Практический смысл в том, что функция «какая стадия следующая» для них обязана вернуть «никакая» — иначе автомат зациклится. Отдельно стоит blocked: он выглядит как тупик, но выход из него есть — через действие человека, а не автоматически.

Стадию context из оригинала мы объединим с plan — сбор контекста станет функцией, которую зовёт планировщик. Отдельной стадией она нужна там, где контекст дорогой и его хочется кэшировать в stage_results; у нас он дешёвый.

Почему PIPELINE — массив, а не объект-словарь переходов? Потому что пайплайн линейный, и массив делает это очевидным: любой, кто откроет файл, за секунду увидит порядок. МОДУЛЬ 02

Хранилище задач

Одна SQLite-база на всю систему — и никакого другого состояния.

Теория

Правило, которое стоит принять до написания первой строки: в памяти процесса не живёт ничего важного. Всё, что нужно для продолжения работы, лежит в SQLite. Убей worker kill -9 в любой момент — после перезапуска система должна продолжить.

Из этого правила вытекает форма API хранилища. Не «создать задачу», а upsertTask: worker может увидеть тот же issue второй раз, и это должно быть безобидно.

Upsert — склейка слов update и insert: «обнови, если такая запись есть, иначе создай». Нужен там, где одну и ту же операцию могут выполнить дважды. Наш worker опрашивает GitHub каждые пятнадцать секунд и каждый раз видит те же issue; будь у нас обычный insert, при втором проходе мы получили бы дубликаты задач.
UNIQUE — ограничение на колонку таблицы: база не даст вставить вторую строку с тем же значением. Мы вешаем его на issue_number, и это страховка на уровне базы: даже если в коде окажется ошибка и мы попробуем вставить дубль, база откажет с ошибкой вместо того, чтобы молча создать вторую задачу по тому же issue. Проверка в коде и ограничение в базе — не замена друг другу, они работают вместе.

Про better-sqlite3 и синхронность: она здесь не компромисс, а преимущество. Пайплайн выполняется последовательно, параллелизма внутри задачи нет, а синхронные вызовы означают, что между «прочитал состояние» и «записал состояние» гарантированно ничего не вклинилось.

Один режим включить обязательно: PRAGMA journal_mode = WAL. Без него читающий процесс (API) будет блокировать пишущий (worker) — и наоборот. У нас ровно этот случай: два процесса, одна база.

PRAGMA — команда настройки самой SQLite, а не запрос к данным. Синтаксис похож на SQL, но она меняет поведение движка: режим журналирования, размер кэша, проверку внешних ключей. Выполняется один раз при открытии базы.
WAL (write-ahead log, «журнал упреждающей записи») — режим, в котором изменения сначала дописываются в отдельный файл-журнал, а в основной файл базы переносятся позже. Практический эффект ровно один, и он нам нужен: читатели не блокируют писателя, а писатель не блокирует читателей. В режиме по умолчанию SQLite блокирует файл целиком, и наш API, читающий события два раза в секунду, регулярно мешал бы worker'у писать. Включается одной строкой и навсегда — режим сохраняется в самом файле базы.
Задание
  1. src/db.ts — открывает базу по config.dbPath, включает WAL, создаёт папку под файл базы, если её нет, создаёт таблицу tasks через CREATE TABLE IF NOT EXISTS и экспортирует единственный инстанс db. Никаких классов-обёрток: better-sqlite3 синхронный, соединение одно на процесс.

  2. src/state.ts — пять функций, и больше туда ничего не лезет:

  issueNumber: number;
  issueTitle: string;

Что делает upsertTask. Название — от «update or insert». Задача с таким issueNumber уже есть — обновляются только заголовок и тело, и возвращается существующая запись; status и stage при этом не трогаются. Нет — создаётся новая в pending/fetch с нулём попыток. Возвращается в обоих случаях полный Task, уже перечитанный из базы. Поведение «не сбрасывать статус» здесь главное: syncIssues() из модуля 8 будет звать upsertTask на каждом обороте worker'а, и без этого правила работающая задача бесконечно откатывалась бы в начало.

Что такое patch в updateTask. Объект с любым подмножеством полей: updateTask(id, { status: "running" }) или updateTask(id, { stage: "verify", attempts: 1 }). Обновляются только переданные ключи, updated_at проставляется сам. Изменяемых полей ровно шесть — status, stage, attempts, branch, worktreePath, prUrl; заведи их белым списком и молча игнорируй всё остальное, иначе кто-нибудь однажды перепишет через patch поле id.

Про имена. Колонки называй в snake_case, а в TypeScript отдавай camelCase. Перевод одного в другое сделай в одном месте — функция rowToTask(row), — чтобы не размазывать по коду.

src/state.ts

import { db } from "./db.js";
import type { Task } from "./types.js";

interface Row {
  id: number; issue_number: number; issue_title: string; issue_body: string;
  status: string; stage: string; attempts: number;
  branch: string | null; worktree_path: string | null; pr_url: string | null;
  created_at: string; updated_at: string;
}

function rowToTask(row: Row): Task {
  return {
    id: row.id,
    issueNumber: row.issue_number,
    issueTitle: row.issue_title,
    issueBody: row.issue_body,
    status: row.status as Task["status"],
    stage: row.stage as Task["stage"],
    attempts: row.attempts,
    branch: row.branch,
    worktreePath: row.worktree_path,
    prUrl: row.pr_url,
    createdAt: row.created_at,
    updatedAt: row.updated_at,
  };
}

const now = () => new Date().toISOString();

export function getTask(id: number): Task | null {
  const row = db.prepare("SELECT * FROM tasks WHERE id = ?").get(id) as Row | undefined;
  return row ? rowToTask(row) : null;
}

export function getTaskByIssue(issueNumber: number): Task | null {
  const row = db
    .prepare("SELECT * FROM tasks WHERE issue_number = ?")
    .get(issueNumber) as Row | undefined;
  return row ? rowToTask(row) : null;
}

export function listTasks(): Task[] {
  const rows = db.prepare("SELECT * FROM tasks ORDER BY id DESC").all() as Row[];
  return rows.map(rowToTask);
}

export function upsertTask(input: {
  issueNumber: number;
  issueTitle: string;
  issueBody: string;
}): Task {
  const existing = getTaskByIssue(input.issueNumber);
  if (existing) {
    db.prepare(
      "UPDATE tasks SET issue_title = ?, issue_body = ?, updated_at = ? WHERE id = ?",
    ).run(input.issueTitle, input.issueBody, now(), existing.id);
    return getTask(existing.id)!;
  }

  const ts = now();
  const info = db
    .prepare(
      `INSERT INTO tasks
         (issue_number, issue_title, issue_body, status, stage, created_at, updated_at)
       VALUES (?, ?, ?, 'pending', 'fetch', ?, ?)`,
    )
    .run(input.issueNumber, input.issueTitle, input.issueBody, ts, ts);
  return getTask(Number(info.lastInsertRowid))!;
}

const MUTABLE = {
  status: "status", stage: "stage", attempts: "attempts",
  branch: "branch", worktreePath: "worktree_path", prUrl: "pr_url",
} as const;

export function updateTask(id: number, patch: Partial<Task>): Task {
  const sets: string[] = [];
  const values: (string | number | null)[] = [];
  for (const [key, column] of Object.entries(MUTABLE)) {
    const value = patch[key as keyof typeof MUTABLE];
    if (value !== undefined) {
      sets.push(`${column} = ?`);
      values.push(value);
    }
  }
  sets.push("updated_at = ?");
  values.push(now(), id);
  db.prepare(`UPDATE tasks SET ${sets.join(", ")} WHERE id = ?`).run(...values);
  return getTask(id)!;
}
Параметризованный запрос — запрос, где вместо значений стоят знаки ?, а сами значения передаются отдельным списком в .run(...). База получает текст запроса и данные по разным каналам и потому никогда не примет данные за команду. Если же склеивать SQL строками ("... WHERE id = " + id), то значение 1; DROP TABLE tasks станет частью команды — это и есть SQL-инъекция. Правило простое: значения — всегда через ?, без исключений.

Есть нюанс: через ? передаются только значения. Имя таблицы или колонки так подставить нельзя — его придётся вклеить в строку запроса. Поэтому имена колонок берут исключительно из своего списка в коде и никогда из входных данных.

Словарь MUTABLE — не украшательство, а защита: он задаёт белый список колонок, которые вообще можно обновлять через updateTask. Без него легко получить SQL-инъекцию через имя ключа в patch. Значения и так параметризованы через ?, но имена колонок в SQL параметром не передашь — их надо брать только из своего списка, никогда из входных данных.

МОДУЛЬ 03

Append-only лог событий

Один механизм, который потом окажется и стримом, и отладчиком, и историей.

Теория

Таблица tasks отвечает на вопрос «где задача сейчас». Она не отвечает на вопрос «как она туда попала»: когда мы делаем UPDATE и меняем статус с running на done, прежнее значение исчезает навсегда. Поэтому рядом живёт вторая таблица, task_events.

Append-only — «только дописывание». В такую таблицу делают исключительно INSERT: строки никогда не изменяют и не удаляют. Каждый шаг системы добавляет запись «что произошло» — стадия началась, стадия закончилась за 4200 мс, агент прочитал файл. История получается полной и неизменяемой, и по ней можно восстановить весь ход задачи, даже если её текущее состояние давно другое. Знакомый аналог — история коммитов в git: коммиты дописываются, а не редактируются.

Ключевая деталь — колонка seq.

seq — порядковый номер события внутри своей задачи: 1, 2, 3, 4… Не сквозной через всю базу, а свой у каждой задачи, и всегда только растущий (никогда не уменьшается и не переиспользуется). Выглядит это так: 
task_id | seq | stage     | kind
--------+-----+-----------+----------------
      7 |   1 | plan      | stage_started
      8 |   1 | plan      | stage_started     ← у задачи 8 своя нумерация
      7 |   2 | plan      | stage_finished
      8 |   2 | plan      | stage_finished
      7 |   3 | implement | stage_started

Почему нумерация именно локальная для задачи, а не сквозной автоинкремент по всей таблице? Три причины:

  1. Клиент, подписавшийся на задачу, может сказать «у меня всё до 42-го, дай дальше» — и это работает независимо от активности других задач.
  2. seq идёт в SSE как id:, а браузер при обрыве связи сам пришлёт его обратно в заголовке Last-Event-ID. Восстановление после разрыва получается бесплатно.
  3. События можно надёжно сортировать. По ts_ms нельзя: два события в одной миллисекунде — обычное дело.

Теперь неочевидное. Номер мы вычисляем сами: «взять максимальный seq у этой задачи и прибавить единицу». Между «посмотрел максимум» и «вставил строку» проходит время, и если писать будут двое, оба могут увидеть один и тот же максимум и попытаться занять один номер.

Составное UNIQUE — ограничение уникальности не на одну колонку, а на пару: UNIQUE (task_id, seq). Оно требует, чтобы сочетание значений не повторялось. Пары (7, 1) и (8, 1) прекрасно уживаются — а вот вторая (7, 1) уже не пройдёт.

Это ограничение мы используем не как проверку, а как механизм: пусть оба писателя попробуют вставить строку, база пропустит только одного, а второй получит ошибку нарушения уникальности, перечитает максимум (он уже вырос) и повторит. Никаких блокировок и ожиданий — проигравший просто пробует ещё раз. В оригинале сделано ровно так: цикл с перехватом IntegrityError в events.py.

payload — «полезная нагрузка» события: произвольные данные, которые к нему прилагаются. У разных событий они разные — у «стадия закончилась» это длительность и результат, у «агент вызвал инструмент» — имя инструмента и путь к файлу. Заводить под каждый вариант свои колонки бессмысленно, поэтому payload складывают в одну текстовую колонку как JSON: при записи JSON.stringify, при чтении JSON.parse. Плата за гибкость — база не знает, что там внутри, и искать по содержимому payload неудобно.

Второй кирпич — обёртка withStage. Каждая стадия должна порождать пару событий (started + finished) или пару (started + failed), с замером длительности. Если это писать руками в каждой стадии, рано или поздно кто-то забудет — и в UI появится вечно крутящийся спиннер. Обёртка делает забывание невозможным.

Задание

src/events.ts

import { db } from "./db.js";
import type { EventKind, Stage, TaskEvent } from "./types.js";

export function recordEvent(
  taskId: number,
  stage: Stage,
  kind: EventKind,
  payload: Record<string, unknown> = {},
): number {
  const json = JSON.stringify(payload);
  const tsMs = Date.now();

  // MAX(seq)+1 без блокировок: конкурент проиграет на UNIQUE и мы повторим.
  for (;;) {
    const { next } = db
      .prepare("SELECT COALESCE(MAX(seq), 0) + 1 AS next FROM task_events WHERE task_id = ?")
      .get(taskId) as { next: number };
    try {
      db.prepare(
        `INSERT INTO task_events (task_id, seq, stage, kind, ts_ms, payload)
         VALUES (?, ?, ?, ?, ?, ?)`,
      ).run(taskId, next, stage, kind, tsMs, json);
      return next;
    } catch (err) {
      if (!String(err).includes("UNIQUE")) throw err;
    }
  }
}

export function readEvents(taskId: number, afterSeq = 0): TaskEvent[] {
  const rows = db
    .prepare(
      `SELECT seq, task_id, stage, kind, ts_ms, payload
         FROM task_events
        WHERE task_id = ? AND seq > ?
        ORDER BY seq ASC`,
    )
    .all(taskId, afterSeq) as Array<{
      seq: number; task_id: number; stage: string;
      kind: string; ts_ms: number; payload: string;
    }>;

  return rows.map((r) => ({
    seq: r.seq,
    taskId: r.task_id,
    stage: r.stage as Stage,
    kind: r.kind as EventKind,
    tsMs: r.ts_ms,
    payload: JSON.parse(r.payload) as Record<string, unknown>,
  }));
}

export async function withStage<T>(
  taskId: number,
  stage: Stage,
  fn: () => Promise<T>,
  input: Record<string, unknown> = {},
): Promise<T> {
  recordEvent(taskId, stage, "stage_started", { input });
  const startedAt = Date.now();
  try {
    const result = await fn();
    recordEvent(taskId, stage, "stage_finished", {
      durationMs: Date.now() - startedAt,
      output: result,
    });
    return result;
  } catch (err) {
    recordEvent(taskId, stage, "stage_failed", {
      durationMs: Date.now() - startedAt,
      error: err instanceof Error ? err.message : String(err),
    });
    throw err;
  }
}

В оригинале в payload'е ещё режутся длинные строки: поле больше 64 КБ заменяется на обрезок с маркером truncated. Мы это пропускаем, но знай, зачем оно: без обрезки один ответ модели с большим файлом раздувает и базу, и каждый SSE-кадр, и UI начинает лагать на ровном месте.

МОДУЛЬ 04

Оркестратор пайплайна

Сердце системы. Пока со стадиями-заглушками — но со всей настоящей механикой.

Теория

Оркестратор отвечает на четыре вопроса, и ни на один из них не отвечает модель.

1. Порядок. Стадии идут по PIPELINE, единственное ветвление — петля implement ⇄ verify.

2. Идемпотентность. Перед выполнением стадия смотрит в таблицу stage_results: если результат за эту стадию (и эту попытку) уже есть — стадия пропускается, результат берётся из базы. Это то самое свойство, ради которого всё затевалось: перезапустил worker после падения на verify — заново отработает только verify, а не дорогой implement.

Идемпотентность — свойство операции, при котором повторный запуск не меняет результат по сравнению с первым. Нажать «сохранить» дважды и получить одну запись вместо двух — это идемпотентность. Обратный пример: «прибавить единицу к счётчику» — не идемпотентно, два запуска дадут разный итог. Для нас это способ пережить падение: раз повторный запуск стадии безопасен, можно просто перезапустить worker и не думать, на чём именно он упал.

Ключ у stage_results составной: (task_id, stage, attempt) — то есть уникальна не стадия сама по себе, а сочетание «задача + стадия + номер попытки». Без attempt вторая попытка implement нашла бы сохранённый результат первой и не сделала бы ничего.

3. Политика ошибок. Тут есть неочевидная асимметрия. Всё, что падает до первой записи в worktree (fetch, plan), почти всегда падает по инфраструктурным причинам — сеть, токен, rate limit. Такая задача возвращается в pending и будет подхвачена следующим проходом. Всё, что падает после — это уже содержательный провал, задача уходит в failed. В оригинале это константа PRE_IMPLEMENT_STAGES.

4. Бюджет попыток. Петля implement → verify крутится не более MAX_ATTEMPTS раз. Каждая следующая попытка получает не только план, но и отчёт о провале предыдущей.

В этом модуле стадии — заглушки: fetch ничего не делает, plan возвращает фиктивный текст, implement спит секунду, verify возвращает passed: true. Смысл в том, чтобы отладить каркас — переходы, идемпотентность, события — до того, как в него въедут сеть и LLM.

Задание
  1. Таблица stage_results и две функции в state.ts. Колонки: task_id, stage, attempt, output_json, created_at, и PRIMARY KEY (task_id, stage, attempt).

  taskId: number, stage: Stage, attempt?: number,

    attempt входит в ключ, потому что implement и verify выполняются по нескольку раз. У стадий, которые крутятся ровно один раз (fetch, plan, pr), attempt всегда 0.

  2. src/pipeline.ts — оркестратор:

    Прогоняет задачу от её текущей стадии до done или failed. Ничего не возвращает: весь результат работы — это строки в базе. Внутри удобно завести приватный хелпер «выполнить стадию один раз»:

  task: Task, stage: Stage, attempt: number, fn: () => Promise<T>,

    который делает четыре вещи подряд: смотрит getStageResult и при попадании сразу возвращает сохранённое, ставит задаче stage + status: "running", зовёт withStage, кладёт результат в saveStageResult. Дальше runTask состоит из вызовов once и ветвлений между ними:

    • implement → verify в цикле for (attempt = 1; attempt <= config.maxAttempts; attempt++); прошло — выходим из цикла, не прошло и попытки кончились — бросаем ошибку;

  3. src/stages/ — четыре файла-заглушки. У каждой стадии свой файл и своя функция run, а результат — собственный интерфейс, объявленный в том же файле:

Импортируй их в пайплайн через import * as planStage from "./stages/plan.js": в модулях 8–13 ты заменишь только тела, а пайплайн не заметит.

  4. src/worker.ts — берёт из listTasks() все задачи в статусе pending (и running — это недоделанные с прошлого запуска) и по очереди прогоняет через runTask. Пока это один проход и выход; бесконечным цикл станет в модуле 8.

Сигнатуры стадий здесь ещё не финальные: в модуле 9 каждой рабочей стадии добавится второй параметр worktreePath. Это оговорено в задании того модуля — не пугайся, когда дойдёшь.

src/pipeline.ts

import { config } from "./config.js";
import { recordEvent, withStage } from "./events.js";
import { getStageResult, saveStageResult, updateTask } from "./state.js";
import type { Stage, Task } from "./types.js";

import * as fetchStage from "./stages/fetch.js";
import * as planStage from "./stages/plan.js";
import * as implementStage from "./stages/implement.js";
import * as verifyStage from "./stages/verify.js";
import * as prStage from "./stages/pr.js";

const PRE_IMPLEMENT: Stage[] = ["fetch", "plan"];

/** Выполнить стадию один раз: если результат уже сохранён — вернуть его. */
async function once<T>(
  task: Task, stage: Stage, attempt: number, fn: () => Promise<T>,
): Promise<T> {
  const cached = getStageResult<T>(task.id, stage, attempt);
  if (cached) return cached;

  updateTask(task.id, { stage, status: "running" });
  const result = await withStage(task.id, stage, fn, { attempt });
  saveStageResult(task.id, stage, result, attempt);
  return result;
}

export async function runTask(task: Task): Promise<void> {
  let current = task.stage;
  try {
    await once(task, "fetch", 0, () => fetchStage.run(task));

    const plan = await once(task, "plan", 0, () => planStage.run(task));
    if (plan.needsHuman) {
      recordEvent(task.id, "plan", "blocked", { questions: plan.text });
      updateTask(task.id, { status: "blocked", stage: "plan" });
      return;
    }

    let verification = { passed: false, report: "" };
    for (let attempt = 1; attempt <= config.maxAttempts; attempt++) {
      current = "implement";
      const impl = await once(task, "implement", attempt, () =>
        implementStage.run(task, plan.text, verification.report),
      );

      current = "verify";
      verification = await once(task, "verify", attempt, () =>
        verifyStage.run(task, impl),
      );

      if (verification.passed) break;
      if (attempt === config.maxAttempts) {
        throw new Error(`verify failed after ${attempt} attempts: ${verification.report}`);
      }
    }

    current = "pr";
    const pr = await once(task, "pr", 0, () => prStage.run(task, verification.report));
    updateTask(task.id, { stage: "done", status: "done", prUrl: pr.url });
  } catch (err) {
    const message = err instanceof Error ? err.message : String(err);
    if (PRE_IMPLEMENT.includes(current)) {
      // Инфраструктурный сбой до первой записи в worktree — вернуть в очередь.
      updateTask(task.id, { status: "pending", stage: "fetch" });
    } else {
      updateTask(task.id, { status: "failed", stage: "failed" });
    }
    console.error(`task ${task.id} stopped at ${current}: ${message}`);
  }
}

МОДУЛЬ 05

HTTP API

Второй процесс, который знает о первом только через файл базы.

Теория

API у нас почти полностью на чтение — и это не случайность. Пайплайн — процесс долгий (минуты), а HTTP-запрос — короткий. Попытка запустить задачу прямо в обработчике роута заканчивается таймаутом на клиенте и висящей задачей на сервере.

Поэтому разделение такое: worker пишет, API читает. Единственные пишущие эндпоинты меняют не результат, а намерение — «поставь эту задачу обратно в очередь». Кто и когда её реально выполнит — дело worker'а.

Второе, о чём стоит подумать заранее, — проекция. UI не должен получать сырые строки таблицы: ему нужно, например, знать не только текущую стадию, но и состояние каждой стадии (не начата / идёт / готово / упала), чтобы нарисовать степпер. Это выводится из лога событий. Считать такое на клиенте — значит дублировать логику в двух местах; считаем на сервере, отдаём готовое.

Проекция — представление данных, посчитанное из хранимых, но не хранящееся отдельно. Мы не держим в базе колонку «статус стадии plan» — мы выводим её из событий каждый раз при запросе. Термин пришёл из event sourcing, где хранят только поток событий, а любое состояние получают, «проиграв» этот поток. По духу это то же, что вычисляемое значение из хранимых полей: источник правды один, производное считается на лету.
Задание

1. src/projection.ts — превращение сырых событий в то, что рисует UI. Отдельный файл, потому что это чистая логика без Express:

  stage: Stage;

  durationMs: number | null;   // null, пока стадия не завершилась

  stages: StageView[];

projectStages проходит по PIPELINE и для каждой стадии смотрит только её события: был stage_failed — failed; был stage_finished — done; был только stage_started — running; не было ничего — pending. durationMs берётся из payload завершающего события.

projectTask отдаёт задачу с приклеенным массивом стадий; флаг withEvents решает, класть ли туда ещё и события (в списке они не нужны, в карточке нужны — последние 200).

src/projection.ts

import { PIPELINE } from "./types.js";
import type { Stage, Task, TaskEvent } from "./types.js";

export interface StageView {
  stage: Stage;
  status: "pending" | "running" | "done" | "failed";
  durationMs: number | null;
}

export function projectStages(events: TaskEvent[]): StageView[] {
  return PIPELINE.map((stage) => {
    const own = events.filter((e) => e.stage === stage);
    const finished = own.find((e) => e.kind === "stage_finished");
    const failed = own.find((e) => e.kind === "stage_failed");
    const started = own.find((e) => e.kind === "stage_started");

    const terminal = failed ?? finished;
    const status = failed ? "failed" : finished ? "done" : started ? "running" : "pending";

    return {
      stage,
      status,
      durationMs: terminal ? Number(terminal.payload.durationMs ?? 0) : null,
    };
  });
}

export function projectTask(task: Task, events: TaskEvent[], withEvents: boolean) {
  return {
    ...task,
    stages: projectStages(events),
    events: withEvents ? events.slice(-200) : undefined,
  };
}

МОДУЛЬ 06

Живой поток: SSE поверх SQLite

Как сделать реалтайм между двумя процессами, не заводя брокер.

Теория

Нужно, чтобы события, которые worker пишет в базу, немедленно появлялись в браузере. Три варианта:

ВариантПочему не он
WebSocketДвусторонний канал там, где нужен односторонний. Плюс своя логика переподключения и восстановления пропущенного.
Опрос GET /api/tasks/:id с клиентаРаботает, но задержка и трафик растут вместе с числом открытых вкладок; каждый опрос тащит всю задачу целиком.
SSEОдносторонний поток — ровно то, что нужно. Браузер сам переподключается и сам присылает Last-Event-ID.

Остаётся вопрос: как процесс API узнает, что worker написал новое событие? Между процессами общей памяти нет, значит event emitter не годится. Ответ прост до неприличия: API опрашивает таблицу раз в 500 мс запросом readEvents(taskId, lastSeen).

Поллинг (polling, опрос) — периодически спрашивать «что нового?» вместо того, чтобы получать уведомление. Противоположность — push, когда источник сам сообщает об изменении. Поллинг считается грубым решением, но у него есть свойство, которого нет у push: он не зависит от того, слушал ли ты в момент события. Пропустил уведомление — потерял его навсегда; при опросе просто прочитаешь всё, что накопилось.

Это звучит как костыль, но подумай: индексированный запрос по (task_id, seq) в локальном SQLite стоит десятки микросекунд. Два раза в секунду на подписчика — шум. Взамен мы получаем свойство, которого у in-memory шины нет в принципе: подписчику всё равно, был ли он подключён, когда событие произошло. Он всегда читает из журнала, а не ловит широковещание. Обрыв связи, перезапуск API, подключение через час — во всех случаях один и тот же код.

Формат кадра SSE — текстовый и строгий:

id: 42
event: stage_finished
data: {"seq":42,"stage":"plan","kind":"stage_finished","payload":{...}}

Пустая строка в конце обязательна — она и есть разделитель кадров. Поле id браузер запоминает и вернёт в Last-Event-ID. Поле event определяет, на какое имя события сработает addEventListener; если его не указывать, всё придёт в onmessage.

Задание

Добавь в src/server.ts пятый роут — GET /api/tasks/:id/events. Обычный обработчик Express, который просто никогда не зовёт res.end():

  1. Заголовки ответа — до первой записи в поток: Content-Type: text/event-stream, Cache-Control: no-cache, Connection: keep-alive, X-Accel-Buffering: no (последний отключает буферизацию в nginx, если он однажды окажется впереди; без него кадры копятся и приезжают пачкой).
  2. Стартовая позиция. const lastSeen = Number(req.headers["last-event-id"] ?? 0). Браузер присылает этот заголовок сам при переподключении — руками его слать не надо.
  3. Первый проход — сразу, не дожидаясь таймера: подписчик должен получить накопившееся мгновенно, а не через полсекунды.
  4. Дальше setInterval на 500 мс, и на каждом тике одно и то же: readEvents(taskId, lastSeen) → на каждое событие пишешь кадр → двигаешь lastSeen на его seq. Формат кадра — из теории выше; кадр обязан заканчиваться пустой строкой, то есть \n\n.
  5. На req.on("close") — clearInterval.

Последний пункт — не формальность: забытый setInterval на закрытом соединении будет вечно писать в мёртвый сокет и течь памятью на каждой перезагрузке страницы. Проверить легко — открой и закрой вкладку десять раз и посмотри, сколько таймеров осталось живо.

Как проверить себя
curl -N localhost:8000/api/tasks/1/events

Сначала прольются все накопленные события, потом соединение останется открытым. Запусти в другом терминале worker на этой задаче — новые кадры должны появляться в curl в реальном времени. Проверь и докачку: curl -N -H "Last-Event-ID: 5" ... — должно начаться с шестого события.

Эталонное решение

src/server.ts — добавить

const POLL_MS = 500;

app.get("/api/tasks/:id/events", (req, res) => {
  const taskId = Number(req.params.id);

  res.writeHead(200, {
    "Content-Type": "text/event-stream",
    "Cache-Control": "no-cache",
    Connection: "keep-alive",
    "X-Accel-Buffering": "no",
  });

  let lastSeen = Number(req.headers["last-event-id"] ?? 0) || 0;

  const tick = () => {
    for (const event of readEvents(taskId, lastSeen)) {
      lastSeen = event.seq;
      res.write(`id: ${event.seq}\n`);
      res.write(`event: ${event.kind}\n`);
      res.write(`data: ${JSON.stringify(event)}\n\n`);
    }
  };

  tick();
  const timer = setInterval(tick, POLL_MS);

  req.on("close", () => {
    clearInterval(timer);
    res.end();
  });
});

Заголовок X-Accel-Buffering: no нужен, если между браузером и Node окажется nginx: по умолчанию он буферизует ответ и «копит» кадры, превращая реалтайм в пакетную доставку раз в несколько секунд. Локально без прокси он безвреден, но привыкать ставить его стоит — отлаживать такое на проде мучительно.

МОДУЛЬ 07

React UI

Момент, когда проект перестаёт быть набором скриптов.

Теория

Главная механика фронтенда здесь — склейка снапшота и потока. При открытии задачи мы делаем две вещи одновременно: тянем GET /api/tasks/:id (там уже есть последние события) и открываем EventSource. Оба источника дают пересекающиеся множества событий.

Решение — не пытаться их синхронизировать, а сделать слияние идемпотентным: держать Set из виденных seq и молча отбрасывать дубли. Тогда порядок прихода перестаёт иметь значение, и весь класс гонок исчезает. Именно так сделано в оригинальном useTaskStream.ts.

Про EventSource надо знать три вещи:

  • Нельзя задать заголовки. Никакого Authorization. Авторизация для SSE — только куки или токен в query-строке.
  • Переподключается сам. При обрыве браузер сам сделает новый запрос и сам подставит Last-Event-ID из последнего виденного id:. В onerror закрывать соединение не надо — этим ты как раз сломаешь автопереподключение.
  • Именованные события идут мимо onmessage. Раз мы пишем event: stage_finished, нужен addEventListener("stage_finished", ...) на каждое имя.

И про Vite: dev-сервер поднимается на 5173, API на 8000 — это разные origin. Вместо возни с CORS проще настроить прокси в vite.config.ts, тогда фронт ходит на относительный /api/..., и в проде ничего менять не нужно.

Задание
  1. Подними Vite + React + TS в web/ и добавь в vite.config.ts прокси /api на http://localhost:8000. Прокси нужен, чтобы фронт и API выглядели для браузера одним origin — иначе придётся возиться с CORS, а EventSource с ним особенно капризен.
  2. web/src/types.ts — скопируй туда Stage, TaskStatus, EventKind, Task, TaskEvent, StageView и TaskView. Да, дублирование; общий пакет ради семи типов — оверинжиниринг для учебного проекта, а вот забыть обновить копию — реальный риск, так что держи файл на виду.
  3. Хук useTaskStream: 
    export function useTaskStream(taskId: number | null): {
  task: TaskView | null;   // снапшот из GET /api/tasks/:id
  events: TaskEvent[];     // отсортированы по seq
  connected: boolean;      // открыт ли SSE прямо сейчас
};

    Что он делает по шагам: при смене taskId тянет снапшот GET /api/tasks/:id, кладёт его события в состояние, затем открывает new EventSource("/api/tasks/" + taskId + "/events") и подписывается на все имена событий из EventKind (напомню: у SSE поле event: — это как раз наш kind, и addEventListener вешается на каждое имя отдельно; на onmessage придёт только то, у чего имени нет).

    Приходящие события сливаются с уже имеющимися с дедупом по seq — снапшот и стрим неизбежно перекроются, и без дедупа лента задвоится. При смене taskId и при размонтировании соединение обязательно закрывается: return () => es.close() в useEffect.

  4. Список задач слева — номер issue, заголовок, статус. Опрос GET /api/tasks раз в 3 секунды обычным setInterval: SSE у нас на одну задачу, а список должен обновляться и без выбранной.
  5. Панель задачи справа — степпер по task.stages (пять кружков с состоянием и длительностью) и под ним лента событий: время, стадия, вид, payload. Ленту держи прокручиваемой и не перерисовывай целиком на каждое новое событие.
  6. Кнопка «Возобновить» — показывается только при task.status === "blocked", дёргает POST /api/tasks/:id/resume.

Стилизуй как хочешь — на оценку не влияет. Важно, чтобы лента не мигала и не теряла события.

Как проверить себя

Открой UI, выбери задачу, запусти worker. События должны появляться в ленте по мере выполнения без перезагрузки. Проверь устойчивость: перезапусти процесс API на середине прогона — через пару секунд поток должен восстановиться сам и без дублей в ленте.

web/src/useTaskStream.ts

import { useEffect, useRef, useState } from "react";
import type { TaskEvent } from "./types";

const KINDS = [
  "stage_started", "stage_finished", "stage_failed", "agent_text", "blocked",
];

export function useTaskStream(taskId: number | null) {
  const [events, setEvents] = useState<TaskEvent[]>([]);
  const [connected, setConnected] = useState(false);
  const seen = useRef(new Set<number>());

  useEffect(() => {
    if (taskId === null) return;

    seen.current = new Set();
    setEvents([]);
    let cancelled = false;

    const merge = (event: TaskEvent) => {
      if (cancelled || seen.current.has(event.seq)) return;
      seen.current.add(event.seq);
      setEvents((prev) => [...prev, event].sort((a, b) => a.seq - b.seq));
    };

    // 1) снапшот
    fetch(`/api/tasks/${taskId}`)
      .then((r) => r.json())
      .then((task) => (task.events ?? []).forEach(merge));

    // 2) поток; дубли отфильтрует merge
    const es = new EventSource(`/api/tasks/${taskId}/events`);
    es.onopen = () => setConnected(true);
    es.onerror = () => setConnected(false);   // не закрываем: браузер переподключится сам

    const handler = (e: MessageEvent<string>) => merge(JSON.parse(e.data));
    for (const kind of KINDS) es.addEventListener(kind, handler);

    return () => {
      cancelled = true;
      es.close();
    };
  }, [taskId]);

  return { events, connected };
}

Гонка (race condition) — ошибка, при которой результат зависит от того, что успело произойти раньше. Здесь: ты кликнул задачу 7, запрос ушёл, ты кликнул задачу 8 — и если ответ по седьмой придёт позже, он допишет её события в ленту восьмой. Код при этом формально правильный, ошибка проявляется только при определённом порядке событий, поэтому «у меня не воспроизводится» — типичная реакция на такой баг.

FETCH: задачи приезжают из GitHub Issues

Issue-трекер как очередь задач — и почему это неожиданно хорошая идея.

Теория

Своя очередь задач потребовала бы своего UI для постановки, своих прав доступа, своих уведомлений и своей истории обсуждений. Всё это уже есть в issue-трекере, и оно уже открыто в соседней вкладке у всех участников. Поэтому очередь — это открытые issue с определённым лейблом.

Лейбл здесь — не косметика, а предохранитель. Без фильтра worker подхватит вообще все issue репозитория, включая обсуждения и баг-репорты, и начнёт писать по ним код. Заведи отдельный лейбл (pico-task) и вешай его руками — это твой рубильник.

Одна ловушка GitHub API, на которой спотыкаются все: эндпоинт issues возвращает и pull request'ы тоже. В модели данных GitHub PR — это issue с дополнительным полем pull_request. Не отфильтруешь — worker начнёт «выполнять» собственные PR.

Логика синхронизации: для каждого найденного issue делаем upsertTask. Уже известные задачи не сбрасываются в начало — обновляется только заголовок и тело. Из результата берём в работу тех, у кого статус pending: остальные либо уже сделаны, либо ждут человека, либо провалились.

}

  await octokit.issues.createComment({

  });

Git worktree — песочница на задачу

Как дать агенту рабочую копию, не отдавая ему свою.

Теория

Агенту нужна файловая система, в которой он может править что угодно. Отдавать ему рабочую копию репозитория нельзя: он оставит незакоммиченные изменения, переключит ветку, а две задачи параллельно перетопчут друг друга.

Полный git clone на задачу решает изоляцию, но платит за это временем и диском — каждый клон тащит всю историю. git worktree даёт то же самое почти бесплатно: несколько рабочих копий поверх одной общей истории объектов. Создание — доли секунды, дисковое потребление — размер одного среза файлов.

Схема такая:

worktrees/
├─ _base/          ← единственный клон, всегда на main, ничего не правим
├─ task-1/         ← worktree, ветка pico/task-1
└─ task-2/         ← worktree, ветка pico/task-2
git worktree — штатная возможность git иметь несколько рабочих папок, подключённых к одному скачанному репозиторию. История коммитов и объекты хранятся один раз в общем месте, а рабочих копий файлов может быть много, каждая на своей ветке. Отличие от нескольких git clone: клон копирует всю историю целиком (долго, много места), worktree — только текущий срез файлов (доли секунды).

Перед созданием worktree базу надо синхронизировать с origin, иначе задача ответвится от вчерашнего main. И перед git worktree add -b имеет смысл удалить одноимённую ветку — иначе повторный прогон задачи упрётся в «branch already exists».

origin, fetch, reset --hard — три вещи, которые здесь работают вместе. origin — стандартное имя удалённого репозитория, того самого на GitHub. git fetch origin скачивает свежие коммиты с сервера, но не трогает твои файлы. git reset --hard origin/main — приводит рабочую копию ровно в то состояние, что на сервере, безжалостно выбрасывая все местные изменения. Для клона-базы это именно то, что нужно: он не место для работы, а всегда точная копия main.

Запуск внешних программ

Дальше нам придётся запускать git, тесты и (в модуле 15) сам CLI-агент. Это отдельный навык, и терминология вокруг него понадобится до конца курса.

Подпроцесс — другая программа, запущенная твоей программой. У неё своя память и свой жизненный цикл; общение с ней идёт через три текстовых потока и одно число: 
stdin   — вход (мы им не пользуемся)
stdout  — обычный вывод программы
stderr  — вывод ошибок и диагностики
exit code — число при завершении: 0 = успех, всё остальное = сбой

Соглашение «ноль значит успех» — общее для всех консольных программ, и на нём держится наша детерминированная проверка из модуля 12: мы не разбираем текст вывода тестов, мы просто смотрим на код возврата.

cwd (current working directory) — рабочий каталог процесса: папка, относительно которой он разрешает относительные пути. Запуская git status с cwd = папка задачи, мы получаем статус именно того worktree, а не того репозитория, из которого запущен worker. Почти во всех наших вызовах cwd задаётся явно — забыть его значит выполнить команду не там, где думаешь.
execFile против exec — два способа запустить программу в Node. exec принимает строку целиком и отдаёт её командной оболочке, из-за чего спецсимволы в данных становятся частью команды: заголовок issue вида fix; rm -rf ~ превратится в две команды. execFile принимает имя программы и массив аргументов, оболочку не задействует, и любая строка внутри массива остаётся просто аргументом. Правило то же, что с SQL: данные никогда не склеиваются с командой.

Про уборку: успешный worktree удаляем, упавший — оставляем. Это позиция оригинала, и она правильная: в упавшем worktree лежит незакоммиченный diff от последней попытки агента. Иногда он на 90% верный, и его дешевле доправить руками, чем гонять задачу заново.

src/shell.ts

import { execFile } from "node:child_process";

export interface ShellResult { stdout: string; stderr: string; code: number }

export function run(
  cmd: string,
  args: string[],
  opts: { cwd?: string; allowFailure?: boolean } = {},
): Promise<ShellResult> {
  return new Promise((resolve, reject) => {
    execFile(cmd, args, { cwd: opts.cwd, maxBuffer: 10 * 1024 * 1024 },
      (err, stdout, stderr) => {
        const code = err && typeof err.code === "number" ? err.code : 0;
        if (err && !opts.allowFailure) {
          reject(new Error(`${cmd} ${args.join(" ")} failed (${code}): ${stderr}`));
          return;
        }
        resolve({ stdout, stderr, code });
      });
  });
}

src/worktree.ts

import fs from "node:fs";
import path from "node:path";
import { config } from "./config.js";
import { run } from "./shell.js";

const basePath = path.join(config.worktreeRoot, "_base");

export async function ensureBaseRepo(): Promise<string> {
  fs.mkdirSync(config.worktreeRoot, { recursive: true });

  if (!fs.existsSync(basePath)) {
    const url = `https://x-access-token:${config.githubToken}@github.com/${config.repo}.git`;
    await run("git", ["clone", url, basePath]);
  }

  await run("git", ["fetch", "origin"], { cwd: basePath });
  await run("git", ["checkout", config.baseBranch], { cwd: basePath });
  await run("git", ["reset", "--hard", `origin/${config.baseBranch}`], { cwd: basePath });
  return basePath;
}

export async function createWorktree(taskId: number) {
  await ensureBaseRepo();

  const worktreePath = path.join(config.worktreeRoot, `task-${taskId}`);
  const branch = `pico/task-${taskId}`;

  if (fs.existsSync(worktreePath)) await removeWorktree(worktreePath);
  await run("git", ["branch", "-D", branch], { cwd: basePath, allowFailure: true });
  await run("git", ["worktree", "add", worktreePath, "-b", branch, config.baseBranch], {
    cwd: basePath,
  });

  return { path: worktreePath, branch };
}

export async function removeWorktree(worktreePath: string): Promise<void> {
  await run("git", ["worktree", "remove", "--force", worktreePath], {
    cwd: basePath,
    allowFailure: true,
  });
}

LLM-агент в минимальной форме

Один вызов Claude на стадию. Никакого цикла инструментов.

Теория

Оригинал запускает полноценные CLI-агенты (Claude Code, Codex), которые сами ходят по файлам десятками инструментальных вызовов. Мы делаем принципиально более простую вещь: один запрос — один ответ. Взамен на нас ложатся две обязанности, которые агент раньше выполнял сам.

Первая — собрать контекст детерминированным кодом. Раз модель не может сама прочитать файл, мы кладём ей в промпт дерево репозитория и содержимое нескольких файлов, выбранных эвристикой (совпадение слов из заголовка issue с именами файлов). Эвристика туповата, и это осознанная цена: в оригинале на её месте TF-IDF плюс долгая память репозитория.

Вторая — забрать результат в машинно-читаемом виде. Просить модель «примени патч» бессмысленно — она не может. Просить выдать unified diff — можно, но парсер diff'а вместе с разрешением смещений контекста — это отдельный проект. Поэтому контракт такой:

{
  "summary": "коротко, что изменено",
  "files": [
    { "path": "src/foo.ts", "content": "<полное новое содержимое файла>" }
  ]
}
diff и патч — diff это описание различий между двумя версиями файла: какие строки убрать, какие добавить и в каком месте. Патч — тот же diff, применяемый к файлу как инструкция. Стандартный формат (unified diff) выглядит как строки с - и + плюс несколько строк неизменного контекста вокруг для ориентира. Сложность в том, что применение патча требует найти этот контекст в файле, а если файл слегка изменился — патч «не ложится». Именно поэтому мы просим у модели не патч, а файл целиком.

Полное содержимое вместо патча — главное упрощение курса. Оно работает для файлов в сотни строк и разваливается на файлах в тысячи. Зато у него нулевая цена реализации и нулевая двусмысленность.

Промпты держим в отдельных .md-файлах, а не в строковых литералах в коде. Причина практическая: промпт — это то, что правят чаще всего, и правки не должны выглядеть в диффе как изменение кода. В оригинале ровно так — каталог agents/prompts/.

import path from "node:path";

type AgentStage = "plan" | "implement" | "verify";

function renderPrompt(
  stage: AgentStage,
  vars: { title: string; body: string; input: string },
): string {
  const template = fs.readFileSync(
    path.join(import.meta.dirname, "prompts", `${stage}.md`), "utf8",
  );
  return template
    .replace("{{title}}", vars.title)
    .replace("{{body}}", vars.body)
    .replace("{{input}}", vars.input);
}

export async function callAgent(
  stage: AgentStage,
  task: { issueTitle: string; issueBody: string },
  input: string,
): Promise<string> {
  const prompt = renderPrompt(stage, {
    title: task.issueTitle, body: task.issueBody, input,
  });

  const response = await client.messages.create({
    model: MODEL,
    max_tokens: 16000,
    messages: [{ role: "user", content: prompt }],
  });

  // content — это union разных блоков (text, thinking, tool_use...).
  // .filter() тип не сужает, поэтому берём текст через flatMap с проверкой.
  return response.content
    .flatMap((block) => (block.type === "text" ? [block.text] : []))
    .join("\n");
}

const SKIP = new Set([".git", "node_modules", "dist", "worktrees", ".venv"]);

function listFiles(root: string, dir = root, acc: string[] = []): string[] {
  for (const entry of fs.readdirSync(dir, { withFileTypes: true })) {
    if (SKIP.has(entry.name)) continue;
    const full = path.join(dir, entry.name);
    if (entry.isDirectory()) listFiles(root, full, acc);
    else acc.push(path.relative(root, full));
  }
  return acc;
}

/** Дерево файлов + содержимое нескольких файлов, похожих на тему issue. */
export function buildContext(
  worktreePath: string,
  task: { issueTitle: string },
): string {
  const files = listFiles(worktreePath);
  const words = task.issueTitle.toLowerCase().split(/\W+/).filter((w) => w.length > 3);

  const relevant = files
    .filter((f) => words.some((w) => f.toLowerCase().includes(w)))
    .slice(0, 5);

  const bodies = relevant.map((f) => {
    const content = fs.readFileSync(path.join(worktreePath, f), "utf8").slice(0, 6000);
    return `### ${f}\n\`\`\`\n${content}\n\`\`\``;
  });

  return [
    "## Файлы репозитория",
    files.slice(0, 200).join("\n"),
    bodies.length ? "\n## Возможно релевантные файлы\n" + bodies.join("\n\n") : "",
  ].join("\n");
}

export interface FileChange { path: string; content: string }

export function parseFilesResponse(
  text: string,
): { summary: string; files: FileChange[] } {
  const fenced = text.match(/```(?:json)?\s*([\s\S]*?)```/);
  const raw = fenced ? fenced[1] : text.slice(text.indexOf("{"), text.lastIndexOf("}") + 1);
  const parsed = JSON.parse(raw) as { summary?: string; files?: FileChange[] };

  if (!Array.isArray(parsed.files)) throw new Error("agent response has no files[]");
  return { summary: parsed.summary ?? "", files: parsed.files };
}

PLAN и остановка ради человека

Непонятная задача — это не ошибка, а штатная ветка автомата.

Теория

Зачем вообще отдельная стадия планирования, если можно сразу просить код? Три причины, и все три практические:

  1. План читаем. Он попадает в лог событий и в UI, и человек за десять секунд понимает, что агент собрался делать, — до того как тот начнёт делать.
  2. План — точка входа в retry. Вторая попытка implement получает тот же план плюс отчёт о провале. Без плана retry превращается в «попробуй ещё раз с нуля», и агент честно генерирует другое, столь же неверное решение.
  3. План — место, где можно остановиться дёшево. Понять, что задача сформулирована непонятно, лучше до правки файлов, а не после.

Отсюда механика остановки. Мы просим модель: если задача противоречива или в ней не хватает данных — вместо плана задай вопросы и заверши ответ строкой NEED_HUMAN. Оркестратор проверяет именно последнюю непустую строку, а не вхождение подстроки: план вполне может обсуждать «нужно уточнить у автора» в теле, и ловить это как сигнал — ложное срабатывание.

Дальше три действия: комментарий с вопросами в issue, статус blocked, событие blocked в лог. Человек отвечает в issue и жмёт «Возобновить» в UI — задача уходит в pending.

Тонкость, о которой легко забыть: при возобновлении надо стереть сохранённый результат стадии plan из stage_results. Иначе идемпотентность, которую мы так старательно строили в модуле 4, честно вернёт кэш — и задача снова заблокируется с теми же вопросами, не увидев ответа человека.

IMPLEMENT, VERIFY и петля попыток

Самый насыщенный модуль: здесь система впервые пишет код и сама себя проверяет.

Теория

Запись файлов. Модель вернула массив {path, content}. Прежде чем что-то писать, каждый путь проверяется на выход за пределы worktree. Модель может вернуть ../../.ssh/authorized_keys — не обязательно злонамеренно, достаточно галлюцинации. Проверка одна и надёжная: path.resolve(worktree, p) должен начинаться с worktree + path.sep. Проверять по наличию .. в строке — не то же самое и обходится.

Верификация в два уровня. Сначала детерминированная команда из .env (тесты, типы, линтер). Ненулевой код — сразу провал, и LLM-ревьюер не вызывается. Причина не в экономии: если код не компилируется, ревью его смысла не имеет, а модель на таком материале склонна отвечать что-нибудь оптимистичное.

Если команды прошли — снимаем git diff и отдаём его второй модели с ролью ревьюера. У ревьюера нарочно ограниченный словарь ответа: PASS первой строкой либо FAIL: причина. Всё остальное — «непонятный вердикт», и это отдельный исход, ведущий к человеку, а не к повтору. Ловушка здесь в том, что при свободном формате ответа парсер начинает угадывать намерение модели, и однажды угадывает неверно в сторону «всё хорошо».

Короткое замыкание (short-circuit) — приём, при котором цепочку проверок прерывают на первом же провале, не выполняя остальные. Здесь у него две причины. Экономическая: не платить за вызов модели впустую. И содержательная: если код не компилируется, ревью не имеет смысла, а модель на таком материале склонна отвечать что-нибудь ободряющее. Ты знаешь этот приём по операторам && и || — принцип тот же.

Одна деталь про diff: новые файлы не попадают в git diff, пока git о них не знает.

Отслеживаемые файлы и индекс — git показывает изменения только для файлов, о которых знает («отслеживаемых»). Только что созданный файл для него — посторонний мусор в папке, и в git diff он не попадёт: получится, что созданные агентом файлы просто не увидит ревьюер. Команда git add -N . («intent to add») регистрирует такие файлы как «собираюсь добавить»: они начинают отображаться в diff, но при этом не готовятся к коммиту полностью — коммит мы делаем отдельно и позже, на стадии PR.

Петля. Провалилась верификация и попытки остались — откатываем worktree через git reset --hard HEAD и заходим на новый круг, передав в промпт отчёт о провале. Откат обязателен: без него вторая попытка начинается поверх сломанного кода первой, и модель чинит собственный мусор вместо решения задачи.

function safeJoin(worktree: string, relative: string): string {
  const full = path.resolve(worktree, relative);
  if (!full.startsWith(worktree + path.sep)) {
    throw new Error(`refusing to write outside worktree: ${relative}`);
  }
  return full;
}

export async function run(
  task: Task,
  worktreePath: string,
  plan: string,
  previousReport: string,
): Promise<ImplementResult> {
  const input = [
    buildContext(worktreePath, task),
    "\n## План\n" + plan,
    previousReport ? "\n## Прошлая попытка провалилась\n" + previousReport : "",
  ].join("\n");

  const response = await callAgent("implement", task, input);
  const { summary, files } = parseFilesResponse(response);

  const written: string[] = [];
  for (const file of files) {
    const full = safeJoin(worktreePath, file.path);
    fs.mkdirSync(path.dirname(full), { recursive: true });
    fs.writeFileSync(full, file.content, "utf8");
    written.push(file.path);
  }

  recordEvent(task.id, "implement", "agent_text", { summary, written });
  return { summary, written };
}

import { callAgent } from "../agent.js";
import { config } from "../config.js";
import { run as sh } from "../shell.js";
import type { Task } from "../types.js";

export interface VerifyResult {
  passed: boolean;
  report: string;
  verdict: "PASS" | "FAIL" | "UNCLEAR";
}

export async function run(task: Task, worktreePath: string): Promise<VerifyResult> {
  // ① детерминированный уровень
  if (config.verifyCommand) {
    const [cmd, ...args] = config.verifyCommand.split(" ");
    const result = await sh(cmd, args, { cwd: worktreePath, allowFailure: true });
    if (result.code !== 0) {
      return {
        passed: false,
        verdict: "FAIL",
        report: `\`${config.verifyCommand}\` завершилась с кодом ${result.code}\n\n` +
          (result.stderr || result.stdout).slice(-2000),
      };
    }
  }

  // ② LLM-ревьюер по diff
  await sh("git", ["add", "-N", "."], { cwd: worktreePath });   // новые файлы → в diff
  const diff = await sh("git", ["diff"], { cwd: worktreePath });
  const response = await callAgent("verify", task, diff.stdout.slice(0, 40000));

  const firstLine = response.split("\n").map((l) => l.trim()).filter(Boolean)[0] ?? "";
  if (firstLine === "PASS") return { passed: true, verdict: "PASS", report: response };
  if (firstLine.startsWith("FAIL")) return { passed: false, verdict: "FAIL", report: response };

  return {
    passed: false,
    verdict: "UNCLEAR",
    report: "непонятный вердикт ревьюера: " + firstLine,
  };
}

  current = "implement";
  await once(task, "implement", attempt, () =>
    implementStage.run(task, workdir, plan.text, verification.report),
  );

  current = "verify";
  verification = await once(task, "verify", attempt, () =>
    verifyStage.run(task, workdir),
  );

  if (verification.passed) break;

  if (verification.verdict === "UNCLEAR") {
    await commentOnIssue(task.issueNumber, "Ревьюер ответил непонятно:\n\n" + verification.report);
    recordEvent(task.id, "verify", "blocked", { report: verification.report });
    updateTask(task.id, { status: "blocked", stage: "verify" });
    return;
  }

  if (attempt === config.maxAttempts) {
    throw new Error(`verify failed after ${attempt} attempts: ${verification.report}`);
  }
}

PR: результат выходит наружу

Единственная стадия, чьи последствия нельзя откатить кнопкой.

Теория

Стадия PR полностью детерминирована — модель здесь не участвует. Последовательность: git add -A → commit → push -u origin <branch> → создание PR через API → комментарий в исходном issue.

Два неочевидных момента.

Автор коммита. В свежем worktree внутри чужого окружения user.name и user.email могут быть не настроены, и git commit упадёт с невнятной ошибкой. Задавай их явно флагами -c — заодно в истории будет честно видно, что коммит машинный.

Одна проверка, две строки кода, спасает ревьюера от очень плохого дня.

import { config, repoOwner, repoName } from "../config.js";
import { commentOnIssue, octokit } from "../github.js";
import { run as sh } from "../shell.js";
import type { Task } from "../types.js";

const MAX_FILES = 40;

export interface PrResult { url: string; number: number; files: number }

export async function run(
  task: Task, worktreePath: string, branch: string, report: string,
): Promise<PrResult> {
  const status = await sh("git", ["status", "--porcelain"], { cwd: worktreePath });
  const changed = status.stdout.split("\n").filter(Boolean);

  if (changed.length === 0) throw new Error("nothing to commit");
  if (changed.length > MAX_FILES) {
    throw new Error(`refusing to commit ${changed.length} files (limit ${MAX_FILES})`);
  }

  await sh("git", ["add", "-A"], { cwd: worktreePath });
  await sh("git", [
    "-c", "user.name=Pico Foundry",
    "-c", "user.email=pico@example.local",
    "commit", "-m", `pico: ${task.issueTitle} (#${task.issueNumber})`,
  ], { cwd: worktreePath });
  await sh("git", ["push", "-u", "origin", branch], { cwd: worktreePath });

  const { data: pr } = await octokit.pulls.create({
    owner: repoOwner,
    repo: repoName,
    head: branch,
    base: config.baseBranch,
    title: `${task.issueTitle} (#${task.issueNumber})`,
    body: [
      `Closes #${task.issueNumber}`,
      "",
      "## Верификация",
      report.trim() || "—",
      "",
      "_Открыто автоматически Pico Foundry._",
    ].join("\n"),
  });

  await commentOnIssue(task.issueNumber, `Готово: ${pr.html_url}`);
  return { url: pr.html_url, number: pr.number, files: changed.length };
}

Слой безопасности

Всё, что пришло от модели или из текста issue, — недоверенный ввод.

Теория

Сформулируем модель угроз честно. Тело issue пишет человек — возможно, не тот, кому ты доверяешь; в публичном репозитории — вообще кто угодно. Этот текст едет прямо в промпт. Ответ модели превращается в файлы на диске и в команды. Значит, между «модель сказала» и «система сделала» обязан стоять фильтр, который не спрашивает у модели разрешения.

Три вектора и три меры.

1. Запись вне worktree. Уже закрыли в модуле 12 функцией safeJoin. Стоит вынести её в security.ts рядом с остальным — чтобы вся граница доверия читалась в одном файле.

2. Опасные команды. Проверка по чёрному списку перед каждым запуском внешней программы. Копируем список оригинала: rm -rf, git push --force, git reset --hard за пределами worktree задачи, переключение на базовую ветку внутри worktree.

Чёрный и белый список — denylist перечисляет то, что запрещено, разрешая всё остальное; allowlist наоборот перечисляет разрешённое, запрещая всё прочее. Белый список безопаснее (неизвестное по умолчанию запрещено), но требует заранее знать весь набор нужных команд — а мы запускаем и git, и произвольную команду тестов из .env. Поэтому здесь чёрный список, и он намеренно короткий: он ловит не злоумышленника, а разрушительную ошибку.

3. Утечка секретов в подпроцесс. Верификационная команда, которую мы гоняем в worktree, — это код из репозитория, и в нём может оказаться что угодно. Запускать его со своими токенами наготове не стоит.

Переменные окружения — набор пар «имя = значение», который операционная система передаёт процессу при запуске; в Node он доступен как process.env. Там же лежат наши секреты из .env. Ключевая деталь: запускаемая программа по умолчанию наследует весь этот набор целиком — вместе с GITHUB_TOKEN и ANTHROPIC_API_KEY. Поэтому подпроцессу передают явно составленный урезанный набор: пути, домашний каталог, локаль — и ничего лишнего.
Prompt injection — приём, при котором во входные данные подкладывают текст, адресованный не программе, а модели: «игнорируй предыдущие инструкции и сделай вот это». Для модели нет разницы между инструкцией разработчика и текстом из тела issue — и то и другое пришло к ней одним куском. Полностью надёжного средства против этого сегодня нет, поэтому защищаются иначе: ограничивают не то, что модель скажет, а то, что система по её словам сделает.

Что этот слой не закрывает — и это стоит проговорить. Prompt injection через тело issue остаётся. Наша защита в том, что у модели нет прямого доступа к shell — она может только вернуть содержимое файлов, а команды выполняет наш код по фиксированному списку. Именно поэтому мы не давали ей tool-use цикл: отсутствие инструмента — самая надёжная песочница.

import path from "node:path";
import { config } from "./config.js";

/** Путь внутри worktree — или исключение. Строковая проверка на ".." дырява. */
export function safeJoin(worktree: string, relative: string): string {
  const full = path.resolve(worktree, relative);
  if (!full.startsWith(path.resolve(worktree) + path.sep)) {
    throw new Error(`path escapes worktree: ${relative}`);
  }
  return full;
}

function isTaskWorktree(cwd: string | undefined): boolean {
  if (!cwd) return false;
  const root = path.resolve(config.worktreeRoot);
  const rel = path.relative(root, path.resolve(cwd));
  return rel.startsWith("task-");
}

export function assertCommandAllowed(
  cmd: string, args: string[], cwd?: string,
): void {
  const line = [cmd, ...args].join(" ");

  if (cmd === "rm" && args.some((a) => a.includes("r") && a.startsWith("-"))) {
    throw new Error(`blocked: ${line}`);
  }
  if (cmd === "git" && args[0] === "push" &&
      args.some((a) => a === "--force" || a === "-f")) {
    throw new Error(`blocked: ${line}`);
  }
  if (cmd === "git" && args[0] === "reset" && args.includes("--hard") &&
      !isTaskWorktree(cwd) && !cwd?.endsWith("_base")) {
    throw new Error(`blocked outside task worktree: ${line}`);
  }
  if (cmd === "git" && (args[0] === "checkout" || args[0] === "switch") &&
      args.includes(config.baseBranch) && isTaskWorktree(cwd)) {
    throw new Error(`blocked: ${line}`);
  }
}

const ENV_ALLOWLIST = ["PATH", "HOME", "LANG", "LC_ALL", "TMPDIR", "SHELL", "USER"];

/** Окружение для чужого кода: без токенов и ключей. */
export function scrubbedEnv(): NodeJS.ProcessEnv {
  const env: NodeJS.ProcessEnv = {};
  for (const key of ENV_ALLOWLIST) {
    if (process.env[key]) env[key] = process.env[key];
  }
  return env;
}

src/shell.ts — с проверкой

import { execFile } from "node:child_process";
import { assertCommandAllowed } from "./security.js";

export function run(
  cmd: string,
  args: string[],
  opts: { cwd?: string; allowFailure?: boolean; env?: NodeJS.ProcessEnv } = {},
): Promise<ShellResult> {
  assertCommandAllowed(cmd, args, opts.cwd);   // единственная точка входа

  return new Promise((resolve, reject) => {
    execFile(cmd, args,
      { cwd: opts.cwd, env: opts.env, maxBuffer: 10 * 1024 * 1024 },
      (err, stdout, stderr) => {
        const code = err && typeof err.code === "number" ? err.code : 0;
        if (err && !opts.allowFailure) {
          reject(new Error(`${cmd} ${args.join(" ")} failed (${code}): ${stderr}`));
          return;
        }
        resolve({ stdout, stderr, code });
      });
  });
}

Агент как подпроцесс CLI

Так устроен настоящий The Foundry — и так у нас в ленте наконец появятся действия агента.

Теория

До сих пор наш агент был «плоским»: мы собирали контекст сами, отправляли один запрос, получали JSON с содержимым файлов. Оригинал устроен иначе, и разница принципиальная — он вообще не ходит в API напрямую. Вместо этого он запускает готовый CLI-агент как подпроцесс и разговаривает с ним через его вывод.

Подпроцессы, потоки stdout/stderr и код возврата мы разобрали в модуле 9 — здесь всё то же самое, только читать вывод придётся не целиком в конце, а по мере поступления.

Команда, которую строит оригинал (src/foundry/agents/claude_cli.py):

claude -p "<промпт>" \
  --output-format stream-json \
  --verbose \
  --max-turns 20 \
  --model sonnet \
  [--resume <session-id>]

Запускается это с cwd = каталог worktree задачи. Для агента это и есть песочница: он видит папку задачи как корень проекта и не знает, что лежит выше.

Отсюда следует главное. У CLI-агента есть собственные инструменты — чтения файлов, правки, поиска, запуска команд. Поэтому промпт ему дают короткий: задачу и план, без содержимого файлов. Всё остальное он выясняет сам, десятками инструментальных вызовов. Наши buildContext и JSON-контракт с полными файлами при таком подходе просто не нужны — они были протезом вместо инструментов.

Как читать вывод

Флаг --output-format stream-json заставляет CLI писать в stdout не человекочитаемый текст, а поток событий в формате NDJSON.

NDJSON (newline-delimited JSON, он же JSON Lines) — формат, где каждая строка это отдельный самостоятельный JSON-объект. В отличие от одного большого JSON-массива, такой поток можно разбирать по мере поступления: прочитал строку — распарсил — обработал, не дожидаясь конца. Именно поэтому его выбирают для стриминга.

Пользователь видит не «стадия implement идёт уже две минуты», а «прочитал src/utils.ts → правит src/utils.ts → запускает тесты». Механика доставки у нас уже построена в модулях 3, 6 и 7; здесь мы просто даём ей содержательный материал.

Построчное чтение (line-buffered) — важная деталь. По умолчанию потоки буферизуются блоками по несколько килобайт: процесс пишет, а читатель ничего не видит, пока буфер не заполнится. Для стрима это смерть — события придут пачкой в конце. В Node это решается тем, что мы читаем stdout через readline, который отдаёт данные по мере прихода строк.

Продолжение сессии

Второй попытке implement нужен не новый разговор с нуля, а продолжение старого — агент уже изучил репозиторий, и терять этот контекст жалко (и дорого). CLI возвращает session_id в событии system; оригинал кладёт его в таблицу agent_sessions и на следующем вызове передаёт --resume <id>, а промпт при этом отправляет короткий — только отчёт о провале.

Почему это отдельный класс, а не правка старого

Мы не выбрасываем прямой вызов API — мы прячем обе реализации за один интерфейс и выбираем нужную переменной окружения. Это тот самый паттерн, что в оригинале назван pluggable backend.

Интерфейс как точка подмены — приём, знакомый тебе по фронтенду (пропс-колбэк, стратегия рендера, адаптер стора). Пайплайн зависит не от «Claude по HTTP», а от абстракции «нечто, что умеет apply(task, worktree, input)». Появится Codex или локальная модель — добавляется файл, пайплайн не меняется ни строкой. И, что важнее для учёбы: с таким интерфейсом можно написать stub-агента и прогонять весь пайплайн офлайн и бесплатно.

Практическая оговорка: этот модуль требует установленного и авторизованного claude CLI. Если его нет — прочитай теорию и посмотри эталонное решение, а рабочим бэкендом оставь API-агент из модуля 10. На остальные модули это не влияет.

import { spawn } from "node:child_process";
import readline from "node:readline";

import { recordEvent } from "../events.js";
import { scrubbedEnv } from "../security.js";
import { getSession, saveSession } from "../state.js";
import type { Task } from "../types.js";
import type { AgentResult, AgentStage, CodingAgent } from "./types.js";

/** Короткая подпись инструмента для ленты: что именно он трогает. */
function toolDetail(input: Record<string, unknown> | undefined): string {
  if (!input) return "";
  const key = ["file_path", "pattern", "command", "url"].find((k) => k in input);
  return key ? String(input[key]).slice(0, 100) : "";
}

export class CliAgent implements CodingAgent {
  name = "claude_cli";

  async apply(
    task: Task, worktree: string, input: string, stage: AgentStage,
  ): Promise<AgentResult> {
    const resumeId = getSession(task.id, stage);

    const args = [
      "-p", input,
      "--output-format", "stream-json",
      "--verbose",
      "--max-turns", "20",
    ];
    if (resumeId) args.push("--resume", resumeId);

    const child = spawn("claude", args, {
      cwd: worktree,
      env: scrubbedEnv(),
      stdio: ["ignore", "pipe", "pipe"],
    });

    let stderr = "";
    child.stderr.on("data", (chunk) => { stderr += String(chunk); });

    let sessionId: string | null = null;
    let response = "";

    // readline отдаёт строки по мере прихода — не ждём конца процесса
    const lines = readline.createInterface({ input: child.stdout });
    for await (const line of lines) {
      if (!line.trim()) continue;

      let event: any;
      try { event = JSON.parse(line); } catch { continue; }  // битую строку пропускаем

      if (event.type === "system" && event.session_id) {
        sessionId = String(event.session_id);
      }

      if (event.type === "assistant") {
        for (const block of event.message?.content ?? []) {
          if (block.type === "tool_use") {
            recordEvent(task.id, stage, "agent_tool", {
              tool: block.name,
              detail: toolDetail(block.input),
            });
          } else if (block.type === "text" && block.text) {
            recordEvent(task.id, stage, "agent_text", { text: String(block.text) });
          }
        }
      }

      if (event.type === "result" && typeof event.result === "string") {
        response = event.result;
      }
    }

    const code: number = await new Promise((resolve) =>
      child.on("close", (c) => resolve(c ?? 0)),
    );
    if (code !== 0) {
      throw new Error(`claude exited with ${code}: ${stderr.slice(-500)}`);
    }

    if (sessionId) saveSession(task.id, stage, sessionId);
    return { response, sessionId };
  }
}

Долгая память репозитория

Пайплайн работает — но каждая задача начинает с чистого листа. Пора это исправить.

Теория

Посмотри на то, что у тебя получилось, глазами агента. Каждая новая задача он видит репозиторий впервые: заново выясняет, где что лежит, заново гадает, какой командой проверяются изменения, и — самое обидное — заново наступает на грабли, на которых споткнулся неделю назад. Вся добытая тяжёлым трудом информация умирает вместе с задачей.

Лечится это одной небольшой таблицей.

Key-value хранилище — простейшая форма базы: пары «ключ → значение», без схемы и без связей. Мы заводим таблицу repo_memory (repo, key, value) с составным первичным ключом (repo, key): у каждого репозитория свой набор ключей, повторно записанный ключ перезаписывает старое значение. Значение кладём как JSON, потому что под ключом может лежать и строка, и список.

И сразу — важное уточнение, потому что слово «память» здесь легко понять неправильно.

Память ≠ дообучение — мы ничего не меняем в модели. Она остаётся ровно такой же, какой была; никакого fine-tuning, никакого «обучения на наших данных». Всё, что происходит, — мы достаём из своей базы текст, добытый в прошлых прогонах, и подклеиваем его в начало промпта. Память живёт в нашем SQLite, а не «внутри» модели, и стирается обычным DELETE.

Что стоит запоминать

Оригинал (workflows.py, функция _save_successful_pr_memory) записывает три вещи после каждого успешно открытого PR — возьмём их же:

КлючЧто внутриЧем полезно на следующей задаче
touched_filesфайлы, которые правилиподсказка, где вообще живёт логика этого проекта
verify_commandкоманда проверки, которая здесь отработалаагент видит, чем именно будут проверять его код
common_failuresотчёты о провалившихся попытках проверкисамое ценное: «вот на чём тут уже падали»

Третий ключ заслуживает отдельного слова. Первые два в принципе можно вытащить из истории git — а вот того, что верификация дважды падала на забытом импорте, в git-истории нет вообще: неудачные попытки туда не попадают, их откатывает git reset --hard. Эта информация существует только у нас, и только потому, что мы завели журнал событий и таблицу результатов стадий.

Гигиена памяти

Память — не свалка, и за ней нужно следить, иначе она превратится в проблему:

  • Размер. Всё, что лежит в памяти, попадает в каждый промпт — то есть прямо в счёт за API. Держи потолок: последние 20 файлов, последние 5 отчётов о провалах.
  • Свежесть. Записи устаревают: файл переименовали, команду проверки поменяли. Мы просто перезаписываем ключи при каждом успехе, и старое вытесняется само.
  • Ошибочная память хуже её отсутствия. Если в common_failures попадёт мусор, агент будет старательно обходить несуществующую проблему. Поэтому пишем память только по успешным задачам: если PR открыт, значит выводы этой задачи чего-то стоят.

В оригинале память читается на стадии context (stages/context.py, функция format_for_prompt) и отдаётся наружу отдельным эндпоинтом GET /api/repos/{repo}/memory, чтобы её можно было посмотреть в UI. Сделаем так же — заглядывать в память полезно, когда агент вдруг начинает вести себя странно.

import { config } from "./config.js";
import { listMemory, listStageResults, saveMemory } from "./state.js";
import type { VerifyResult } from "./stages/verify.js";

const MAX_FILES = 20;
const MAX_FAILURES = 5;

const asStrings = (value: unknown): string[] =>
  Array.isArray(value) ? (value as string[]) : [];

/** Записать выводы задачи. Вызывать только после успешно открытого PR. */
export function rememberSuccess(taskId: number, touchedFiles: string[]): void {
  const memory = listMemory(config.repo);

  // Set убирает повторы, slice держит потолок — иначе список растёт вечно.
  const files = [...new Set([...asStrings(memory.touched_files), ...touchedFiles])];
  saveMemory(config.repo, "touched_files", files.slice(-MAX_FILES));

  if (config.verifyCommand) {
    saveMemory(config.repo, "verify_command", config.verifyCommand);
  }

  const failures = listStageResults<VerifyResult>(taskId, "verify")
    .filter((result) => !result.passed)
    .map((result) => result.report.slice(0, 400));

  if (failures.length) {
    const all = [...asStrings(memory.common_failures), ...failures];
    saveMemory(config.repo, "common_failures", all.slice(-MAX_FAILURES));
  }
}

/** Память в виде куска промпта. Пустая строка, если памяти ещё нет. */
export function formatMemory(): string {
  const memory = listMemory(config.repo);
  const parts: string[] = [];

  const files = asStrings(memory.touched_files);
  if (files.length) {
    parts.push("### Файлы, которые обычно меняют здесь\n" + files.join("\n"));
  }

  if (typeof memory.verify_command === "string") {
    parts.push("### Команда проверки, которая тут работает\n" + memory.verify_command);
  }

  const failures = asStrings(memory.common_failures);
  if (failures.length) {
    parts.push(
      "### На этом уже падали прошлые задачи — не повторяй\n" +
        failures.map((f) => "- " + f.replace(/\n/g, " ")).join("\n"),
    );
  }

  return parts.length ? ["## Опыт прошлых задач", ...parts].join("\n\n") : "";
}

2. Stub-агент для офлайн-прогонов

Интерфейс агента у тебя уже есть с модуля 15 — добавь третью реализацию, stub: она не ходит в сеть, на генерацию кода дописывает строчку в README, на проверку всегда отвечает PASS. Ценность не в самой заглушке, а в том, что с ней весь пайплайн становится проверяемым офлайн, мгновенно и бесплатно. Именно поэтому все 193 теста оригинала не ходят в сеть — а значит, их реально запускают, а не «когда-нибудь потом».

3. Патчи вместо полных файлов

Самое серьёзное ограничение учебной версии. Варианты по возрастанию сложности: попросить модель вернуть замены по принципу «найди этот блок → замени на этот»; выдать ей настоящий tool-use цикл с инструментами чтения и записи; перейти на CLI-агента, как в оригинале. Первый вариант — хорошее следующее упражнение.

4. Параллельность

Сейчас задачи идут по одной. Worktree уже изолированы, так что технически ничего не мешает — но появятся конкуренция за seq (мы к ней готовы — выдача номера построена на повторе при конфликте), за базу (WAL готов) и за лимиты API. Про последнее: у любого платного API есть rate limit — потолок числа запросов за интервал; при его превышении приходит ошибка 429, и правильная реакция на неё — подождать и повторить, а не считать задачу провалившейся. Начни с ограничителя на 2–3 одновременные задачи.

5. Тесты и Docker

Vitest поверх stub-агента и временной базы в tmp — и пайплайн можно рефакторить без страха. Docker Compose на три сервиса с общим томом для базы и worktree делает проект переносимым.

  2. Напиши тест на петлю retry: verify падает дважды — задача должна прийти в failed ровно после MAX_ATTEMPTS попыток.

Как проверить себя

Финальная проверка всего курса, и она же — самая честная: возьми чужой небольшой репозиторий, укажи его в GITHUB_REPO, заведи три разноплановых issue и запусти worker. Система, которая справляется с задачами в проекте, под который её не затачивали, — это уже не учебный пример.
